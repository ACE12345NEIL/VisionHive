I am building a software-only Image and Video Processing project called: VisionHive- “Real-Time Multi-Camera Occupancy and Activity-Aware HVAC Control Using Image and Video Processing”

The project should eventually become a Digital Twin-enabled adaptive HVAC system for a single room.

The system must be completely software-based. No physical CCTV, AC, sensors, ESP32, Arduino or other hardware is required for the core project.

IMPORTANT:
Build the system progressively in clearly defined stages.

Do NOT start with simulation or Digital Twin.

The first stages must build the actual computer vision, environmental modelling, thermal modelling, ML and HVAC-control pipeline using real datasets/video inputs.

Simulation and Digital Twin development must be the FINAL major stage, after the core system is already functional.

TECHNOLOGY STACK:

Backend:
• Python
• FastAPI
• WebSockets

Computer Vision:
• OpenCV
• YOLO / Ultralytics
• ByteTrack or BoT-SORT
• NumPy

Machine Learning:
• Pandas
• scikit-learn
• XGBoost
• PyTorch if required

Database:
• SQLite initially
• Architecture should allow PostgreSQL later

Frontend:
• Lightweight HTML/CSS/JavaScript frontend
• Use a fast visualization/charting library where useful
• Do NOT use Streamlit

The frontend should be modern, visually clean and extremely fast.

STAGE 1 — PROJECT FOUNDATION

Create the basic software architecture.

Implement:

• FastAPI backend
• Lightweight frontend
• WebSocket communication
• SQLite database
• Configuration system
• Logging
• Basic room definition
• Thermal-zone definition
• Dataset management structure

Define one virtual room divided into multiple thermal zones.

Initially use four zones.

Create common data structures for:

• Room
• Zone
• Person
• Device
• Light
• Window
• Door
• HVAC
• Environment

Do not implement the Digital Twin yet.

STAGE 2 — IMAGE AND VIDEO INPUT

Implement the camera/video subsystem.

Support:

• Multiple prerecorded videos
• Webcam input
• Image sequences
• Multiple simultaneous camera feeds

Initially support 2–4 cameras.

Implement:

• Frame extraction
• Frame resizing
• FPS control
• Frame buffering
• Basic image preprocessing

Use OpenCV.

Demonstrate relevant Image Processing concepts such as:

• RGB
• Grayscale
• Resolution
• Gaussian filtering
• Median filtering
• Contrast enhancement
• Histogram processing

The output should be a working multi-camera processing system.

STAGE 3 — PERSON AND OBJECT DETECTION

Implement YOLO-based detection.

Detect at minimum:

• Person
• Laptop
• Computer
• Monitor
• Cell phone where useful
• Server where available
• Other relevant equipment

Every detection should contain:

• Camera ID
• Class
• Confidence
• Bounding box
• Center coordinates
• Timestamp

Create a standardized internal detection format.

STAGE 4 — PERSON TRACKING

Implement multi-frame tracking.

Use:

• ByteTrack
or
• BoT-SORT

Track:

• Person ID
• Position
• Velocity
• Camera ID
• Time detected
• Trajectory

The same person should retain a consistent tracking ID within a camera.

STAGE 5 — ACTIVITY AND MOTION ANALYSIS

Determine how active each detected person is.

Use Image and Video Processing techniques such as:

• Frame differencing
• Optical flow
• Motion estimation
• Bounding-box displacement
• Temporal analysis

Classify activity into a simple scale:

0 = Stationary
1 = Low
2 = Medium
3 = High

Where useful, evaluate a dedicated human activity-recognition model using the Human Activity Recognition video dataset.

STAGE 6 — MULTI-CAMERA FUSION

Combine information from multiple cameras.

The system must prevent double-counting.

If Camera 1 and Camera 2 observe the same person, the system should identify them as one person.

Initially implement:

• Overlapping ROI matching
• Spatial proximity
• Bounding-box characteristics
• Temporal consistency

Then implement a more advanced method using:

• Camera calibration
• Homography
• Common room coordinates

All camera detections should eventually be mapped to a common room coordinate system.

STAGE 7 — THERMAL-ZONE ASSIGNMENT

Map every detected person and device to a thermal zone.

Each zone should maintain:

• People count
• Person locations
• Activity levels
• Device count
• Device load
• Lighting load
• Temperature
• Humidity

Example:

Zone 1:
people = 2
activity = medium
device_load = 400 W

Zone 2:
people = 0
device_load = 100 W

The system must update these values continuously.

STAGE 8 — DEVICE AND LIGHTING ANALYSIS

Use computer vision to detect relevant equipment.

Track:

• PC count
• Laptop count
• Monitor count
• Server count
• Machine count
• Light count

Create a configurable device-power database.

For example, each device type can have:

• Device type
• Estimated power
• Zone
• ON/OFF state

Calculate:

human_heat_load
device_heat_load
lighting_heat_load

Do not treat assumed device power values as universal real-world values. Clearly mark them as configurable assumptions.

STAGE 9 — ENVIRONMENTAL DATA

Integrate indoor environmental data.

Use datasets containing:

• Indoor temperature
• Indoor humidity
• CO2
• Light

• PIR where available
• Occupancy

Normalize the data into a common internal schema.

The primary internal environmental format should contain:

indoor_temperature

indoor_light

Use:

For model training, use historical weather/environmental datasets.

The system must distinguish:

• Real API data

Create the first thermal/heat-load model.

For each zone calculate:

• Human heat
• Device heat
• Lighting heat
• Solar heat
• Outdoor heat transfer
• Window heat gain
• Door effects

The model should be transparent and interpretable.

STAGE 13 — THERMAL RESPONSE MODEL

• Door state
• HVAC state
• HVAC setpoint
• Fan speed
• Airflow direction
• Thermal coupling between zones

The purpose is to understand how the room responds to different conditions before applying ML.

Build an energy-consumption model.

• Total room energy

STAGE 20 — FINAL SIMULATION ENGINE

ONLY AFTER THE ABOVE SYSTEM IS WORKING, introduce the simulation engine.

The simulation engine should reproduce the same inputs that would normally come from cameras, sensors, weather services and HVAC systems.

Allow the user to simulate:

• Adding/removing people
• Changing people between zones
• Changing activity
• Turning PCs on/off
• Changing server load
• Turning lights on/off
• Opening/closing windows
• Opening/closing doors
• Changing louver position
• Changing outdoor temperature
• Changing outdoor humidity
• Changing solar radiation
• Simulating rain
• Changing AC setpoint
• Changing fan speed
• Changing AC mode
• Changing airflow direction
• Increasing device heat
• Sudden occupancy changes
• AC failure
• Different thermal properties

The simulation engine must use the same internal data structures as the real system wherever possible.

This allows the system to switch between:

REAL INPUT MODE

and

SIMULATION MODE

without rewriting the core HVAC/ML pipeline.

IMPORTANT DEVELOPMENT PRINCIPLE:

Do not build the entire project at once.

Each stage must produce a working component before moving to the next stage.

The project should first become a functional real-data computer-vision + thermal + ML + HVAC system.

Only after that should simulation be introduced.

Only after simulation should the Digital Twin be developed.

The final Digital Twin should then use the already-developed real system, models and simulation engine to provide a dynamic virtual representation and what-if analysis.

The final project should demonstrate:

Image Processing
→ Video Processing
→ Computer Vision
→ Multi-Camera Fusion
→ Occupancy Detection
→ Activity Detection
→ Thermal-Zone Mapping
→ Heat-Load Estimation
→ Environmental Modelling
→ Thermal Modelling
→ Machine Learning
→ HVAC Control
→ Energy Analysis
→ Simulation
→ Digital Twin
→ What-If Analysis

The system must clearly distinguish between real observations, historical dataset values, simulated values, ML predictions and Digital Twin state.
